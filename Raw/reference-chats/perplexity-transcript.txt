Problem recap
The SIH problem asks for a privacy-preserving visual browser agent: local on-device vision model reads the screen, automatically detects and redacts sensitive/PII elements, and only then sends sanitized context to a server which produces UI actions or processed data.

Modern browser tooling makes this feasible: WebGPU and WebAssembly now allow running ML models client-side, and libraries like ONNX Runtime Web and Transformers.js expose simple JS APIs for computer vision tasks such as image classification and object detection directly in the browser.

High-level architecture
Design the system as a browser extension + server with a well-defined contract for “sanitized context”:

Browser side (extension):

Content script + background/service worker.

Local vision pipeline using WebGPU/WebAssembly.

DOM + regex PII detection + CSS/canvas masking.

Sanitized context encoder (JSON / low-res image / feature map).

Server side:

LLM/VLM endpoint that consumes sanitized context.

Planner that outputs UI actions (click, type, scroll) or structured assistance.

Existing extensions such as ScreenMask and BlurIt already show that fully local PII detection and masking is viable and practical in real-time extensions, using DOM observers and pattern matching combined with on-page blurs or redaction before screenshots or sharing.

Client-side vision stack
Use Transformers.js or ONNX Runtime Web to run a compact CV model with WebGPU acceleration, falling back to WASM if GPU is unavailable.

Transformers.js supports image classification, object detection, and segmentation tasks out-of-the-box, and can load ONNX models for browser inference.

ONNX Runtime Web provides onnxruntime-web with device options webgpu, webgl, wasm, and webnn, so you can target GPU or CPU depending on the user’s hardware, which is critical for the “client side resource utilization” evaluation metric.

For your use case:

Face & avatar detection: small face detection/segmentation model on ONNX, run via ONNX Runtime Web with deviceType: 'webgpu' when available.

Screen region understanding: lightweight object detection (buttons, form fields, panels) or vision-language model (e.g., Florence-2 in ONNX) via Transformers.js v3 with WebGPU.

There are live demos of running image classification models like MobileNetV4 and Florence‑2 directly on WebGPU using Transformers.js pipelines, indicating that your architecture is realistic for current browsers.

Privacy-preserving PII redaction
For PII detection and redaction, combine DOM-level semantics with vision-level bounding boxes:

Existing tools like ScreenMask and BlurIt detect emails, phone numbers, credit cards, IDs, and other PII using regex + DOM observers and then blur or replace them before screenshots or screen sharing.

Extensions such as Cloak and Redact & Snap show auto-redaction workflows that blur or black out sensitive fields in screenshots and web pages entirely locally without sending data to servers, aligning perfectly with your privacy requirement.

Concretely on the client:

DOM-based filters:

Identify input[type=password], fields with autocomplete hints (email, name, phone), credit card patterns, and IDs using regex similar to ScreenMask’s pattern-matching approach.

Apply CSS masks (blur, pixelate, overlay rectangles), or replace text content with asterisks before rendering a screenshot or serializing context.

Vision-based filters:

Capture the viewport via tabs.captureVisibleTab or draw into an offscreen canvas.

Run vision model; get bounding boxes for faces, avatars, or sensitive widgets.

Paint over those regions (black boxes, heavy blur) in the canvas before encoding to PNG/WebP and sending to the server.

Your “sanitized context” payload can then be:

A redacted screenshot (faces and PII masked), plus metadata about element roles (button, input, etc.).

Or a structured JSON with layout (bounding boxes, element types, partial masked text), which minimises visual content while still giving the server enough state to reason and plan.

Server-side reasoning and actions
On the server, you can use any open-weights LLM/VLM running in the cloud during SIH, as long as it only sees anonymized data.

Design the server with:

Input schema:

Sanitized screenshot (optional).

Structured layout: list of elements with roles, positions, redaction flags, and masked text snippets.

Reasoning engine:

VLM (if using images) to interpret layout and visual cues.

LLM to read the structured layout and task description (“fill this form”, “navigate to X”, etc.), and produce a sequence of high-level UI actions.

The server returns actions like click(element_id), type(element_id, "value"), or scroll(direction="down"), which the extension executes using standard WebExtension APIs and DOM events.

Metrics and evaluation mapping
The SIH evaluation criteria map neatly onto measurable components of your architecture:

Accuracy of visual context (25%):

Measure how well the local vision model and DOM parser reconstruct the screen state into the structured context seen by the server (e.g., recall of buttons, inputs, visible text regions).

Recall/precision for PII detection (20%) & precision of redaction (20%):

Adopt the approach of extensions like ScreenMask and BlurIt that already track detection patterns for emails, phones, and credit cards using regex and validation (e.g., Luhn check for card numbers) to achieve high precision.

Client-side resource utilization (20%):

Use ONNX Runtime Web’s webgpu where available and fall back to wasm for users without GPU support, leveraging the documented guidance on WebGPU flags and adoption (~70% support in late 2024).

Keep models small (tiny/“n” variants), quantized (int8/fp16) as in Florence‑2 WebGPU demos to reduce VRAM and CPU usage.

End-to-end latency (15%):

Real-time WebGPU vision pipelines have already been demonstrated for per-frame processing in browsers, showing that with small models and caching, you can stay within real-time constraints.

Pipeline design: capture → local redaction → encode → send to server → receive actions → execute, with each segment timed and logged.

If the filter fails, the Zap stops and no server call is made, enforcing “redaction before network” at the workflow level.

Step 2: Call server-side LLM/VLM
Step type: Webhooks by Zapier → “POST” or “Custom request”.

Request body:

Pass task_type, screen_layout, and sanitized_image_url (if you use a VLM).

Include any user instruction or agent state needed for planning.

The server hosts your open‑weights LLM/VLM, interprets the sanitized context, and returns a planned action list, e.g.:

json
[
  {"action": "click", "target_id": "submit_button"},
  {"action": "type", "target_id": "email_input", "value": "MASKED_EMAIL"},
  {"action": "scroll", "direction": "down"}
]
Zapier gets this JSON as the output of the webhook step.

Step 3: Branching on response type (Paths)
Step type: Paths by Zapier.

Paths logic:

Path A – UI actions: runs when response_type equals "ui_actions".

Path B – Processed data: runs when response_type equals "summary" or "analysis".

Each path can have its own follow-up actions:

Path A: send actions back to the browser.

Path B: log to Notion/Sheet, send email to user, etc.

Paths let you implement “If response is actions, then do X; if response is data, then do Y” cleanly.

Step 4A: Return UI actions to browser agent
Step type: Webhooks by Zapier → POST to your agent backend or to a URL the extension polls.

Payload: the planned action list and any metadata (confidence, explanations).

Your browser extension then:

Receives this payload.

Maps target_id to DOM elements.

Executes click, type, scroll using standard DOM events.

From Zapier’s perspective, this is just “send JSON to an API”; your extension handles actual browser automation.

Step 4B: Deliver processed data / assistance
If the LLM/VLM response is a summary or analysis instead of UI actions:

Action apps on this path (examples):

Email: send a summary of the page to the user.

Docs: store an anonymized report in Google Docs/Notion.

Chat: push a message to Slack/Discord with recommendations.

Zapier simply routes the sanitized, non‑PII output to wherever the user wants it, leveraging normal Zap “action” steps.

Optional: Logging & observability steps
You can add extra actions after Paths for:

Metrics logging: append to Google Sheets / Airtable rows for latency, detection counts, and agent success.

Alerts: if pii_redaction_status is "failed", create a separate Zap or path to log the incident and notify the team, while still dropping the main workflow.

These are standard multi-step Zap patterns (trigger → filter → paths → actions) and give you a simple way to instrument the SIH metrics in production‑like conditions.

In summary: the PS solution becomes a Zap that’s triggered by your local, privacy-preserving browser agent, gated by filters that ensure redaction succeeded, calls your server LLM/VLM via webhook, then uses paths and actions to either send back UI commands to the agent or deliver processed, anonymized insights to the user.

For the strongest isolation posture, use Chrome Native Messaging rather than a public local HTTP port. Native Messaging lets an extension communicate with a registered native application through stdin/stdout with structured JSON; the extension invokes it from its service worker or extension page, not from the content script.

For hackathon speed, use a loopback-only FastAPI service at 127.0.0.1:8000, then migrate to Native Messaging if you need a stronger security story. Ollama itself exposes its local API at http://localhost:11434/api, and its local endpoint does not require authentication by default—so do not bind it broadly to the network unless ISRO’s internal deployment team adds access control.

Recommended implementation
1. Browser extension: local perception and execution

The extension does four jobs:

Extract safe structural context from the DOM and accessibility attributes.

Capture the viewport.

Detect/redact PII and sensitive visual areas locally.

Execute only validated, allowlisted actions returned by the local runtime.

Use DOM extraction first because it is faster and more accurate for standard browser controls than forcing a vision model to understand every button, input, heading, and form field.

text
DOM / ARIA structure = primary source of UI meaning
Local vision model   = visual fallback and face/region detection
Redaction policy     = security gate before model reasoning
Local LLM / VLM      = task planning
Extension            = trusted execution layer
2. Local vision engine

Run a small ONNX model inside the extension’s offscreen document using WebGPU where available, with WebAssembly as fallback. ONNX Runtime Web supports both WebGPU and WASM/CPU execution; WebGPU is available in modern Chromium browsers, while Firefox compatibility is less uniform and requires validation on your exact target build.

Use the model only for tasks where DOM inspection is insufficient:

Detection target	Implementation	Need a vision model?
Password inputs	input[type=password], autocomplete=current-password	No
Email, phone, cards, PAN/Aadhaar-like IDs	Regex + validators + text-node bounding boxes	No
API keys, tokens, internal URLs	Regex, keyword policy, high-entropy token heuristic	No
Employee IDs / project codes	Configurable regex and DOM-label policy	No
Faces and profile photos	Local face detector in ONNX	Yes
Sensitive map/image regions	On-device segmentation/detection or user-defined region policy	Sometimes
Canvas-only screens / remote desktops	Local OCR + vision detector	Yes
Buttons, forms, labels on ordinary web pages	DOM/ARIA extraction	Usually no
This hybrid design is more lightweight than trying to run a full visual browser agent model for every screen. It also directly improves the resource-utilization metric.
